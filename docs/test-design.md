# Тест-дизайн: применённые техники

Документ показывает, как я превращал требования в проверки. Я использовал классы эквивалентности, граничные значения, таблицу решений, попарное тестирование и диаграмму состояний.

## 1. Классы эквивалентности и границы: totalprice

Требование: цена бронирования — целое положительное число, верхняя граница не задана. Я выделил классы и границы так. Отрицательные значения (-1, -100, -99999) — невалидный класс, ожидаю 400, фактически получил 200 (BUG-07). Ноль оставил под уточнение бизнес-правилом: стенд принимает 200. Значения 1, 100, 150, 829 и 1 000 000 — валидный класс, ответ 200 совпал с ожиданием. Строку ("100", "сто", "") я отнёс к невалидному классу с ожиданием 400, но получил 200, а totalprice сохранился как null (BUG-06). null тоже должен давать 400, но приводит к 500 (BUG-14).

## 2. Границы: даты бронирования

Случай checkout > checkin (01.01 → 05.01) даёт 200 — как и ожидалось. checkout = checkin (01.01 → 01.01) я ожидал отклонить, но стенд отвечает 200. Переставленные даты (checkout < checkin) также проходят с кодом 200 (BUG-08). Прошедшая дата 01.01.2020 принимается (BUG-09). Несуществующее значение 2026-13-45 не только принимается, но и искажается в ответе до 0NaN-aNNaN-... (BUG-13). Формат 01/01/2026 просто принимается. А если передать bookingdates строкой вместо объекта, получаю 500 (BUG-03).

## 3. Границы: имя клиента

Пустая строка "" должна отклоняться, но принимается (BUG-11). null даёт 500 (BUG-02). Значения "A", "Dmitry", "Дмитрий" и "O'Brien-Smith" — валидный класс, ответ 200. Строка из 300 символов должна упереться в лимит длины, но сохраняется целиком (BUG-12).

## 4. Таблица решений: checkout (Swag Labs)

Я разобрал комбинации обязательных полей формы. Когда заполнены First Name, Last Name и Postal Code, происходит переход к Checkout: Overview. Если пуст First Name — ошибка «First Name is required»; пуст Last Name — «Last Name is required»; пуст Postal Code — «Postal Code is required». Когда пусты все три поля, выводятся три сообщения. Ввод одних пробелов я считаю ошибкой, потому что пробелы не являются значением. Спецсимволы стенд не ограничивает, поэтому с ними переход разрешён.

## 5. Попарное тестирование: поля checkout

Факторы: First Name (валидное / пустое / пробелы), Last Name (валидное / пустое), Postal Code (валидное / пустое / буквы). Полный перебор — 3 × 2 × 3 = 18 комбинаций, попарно достаточно 9. Я взял такие пары: (валидное, валидное, валидное), (валидное, пустое, пустое), (пустое, валидное, буквы), (пробелы, пустое, валидное), (валидное, валидное, пустое), (пустое, валидное, валидное), (валидное, пустое, буквы), (пробелы, валидное, буквы) и (пустое, пустое, буквы).

## 6. Диаграмма состояний: бронирование (API)

    [Нет записи]
        | POST /booking (валидные данные)
        v
    [Активная бронь]
        | PUT /booking/{id} + token
        | PATCH /booking/{id} + token
        v
    [Изменённая бронь]
        | DELETE /booking/{id} + token
        v
    [Удалена] -- GET /booking/{id} --> 404

Отдельно проверяю недопустимые переходы: изменение или удаление без токена (403), чтение после удаления (404), обновление несуществующей брони (404/405).

## 7. Предугадывание ошибок (error guessing)

Без отдельного требования я проверил неверный Content-Type, битый JSON, null вместо объекта, неизвестные поля, строку вместо числа, пустое тело запроса, несуществующий ID и невалидный фильтр. Семь из этих проверок выявили дефекты — см. bug-reports.md.
