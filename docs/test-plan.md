# Тест-план

**Проект:** учебное QA-портфолио — тестирование веб-приложения Swag Labs и REST API Restful-Booker  
**Версия документа:** 1.1  
**Период:** 03.11.2026 — 15.11.2026  
**Автор:** автор учебного проекта

---

## 1. Цель

Показать на практике, как я работаю с качеством: тест-дизайн, проверка UI и серверной логики, REST API, оформление тест-кейсов и баг-репортов, базовый SQL.

## 2. Объекты тестирования

Swag Labs (SauceDemo, https://www.saucedemo.com) — демо-магазин: авторизация, каталог, корзина, оформление заказа. Restful-Booker (https://restful-booker.herokuapp.com) — демо-API бронирования: авторизация, CRUD, фильтры. Учебная БД «Банк» — схема clients / accounts / cards / transactions, наполнение и 20 SQL-запросов, запускается локально в SQLite или PostgreSQL.

Стенды публичные и предназначены для обучения. Данные в Restful-Booker периодически сбрасываются, поэтому тесты создают собственные записи.

## 3. Задачи

Я составил чек-листы для UI и API, разработал тест-кейсы с разными техниками тест-дизайна, проверил позитивные и негативные сценарии UI и API, нашёл и оформил дефекты с severity/priority. Дополнительно я подготовил Postman-коллекцию и pytest-набор для API и выполнил 20 SQL-запросов разного уровня (выборка, JOIN, агрегация, подзапросы, оконные функции, DML).

## 4. Область тестирования

В scope UI входят авторизация, каталог и сортировка, корзина, checkout, logout и reset app state. В API — health-check, аутентификация, CRUD бронирований, фильтры, коды ответов, валидация входных данных и авторизация запросов. В SQL — выборки, соединения, агрегаты, подзапросы, оконные функции, изменение данных и индексы.

Вне scope: нагрузочное и security-тестирование, кросс-браузерное тестирование (основной браузер — Chrome), мобильные приложения и адаптивная вёрстка, производительность и доступность (a11y) в полном объёме.

## 5. Подход и виды тестирования

Функциональное тестирование проверяет бизнес-сценарии UI и API по требованиям демо-стендов. Негативное — невалидные типы, пропущенные поля, неверные коды и методы. Регрессионное — повторную проверку CRUD и checkout после изменений данных; smoke — доступность стендов и ключевые сценарии; исследовательское — свободное изучение API для поиска дефектов валидации; интеграционное — связки create → get → update → delete и проверку авторизации; UI/UX — отображение данных, сортировку, счётчики и сообщения об ошибках.

Из техник тест-дизайна я использовал классы эквивалентности и граничные значения (totalprice, длина имён, даты), таблицу решений (комбинации обязательных полей checkout), попарное тестирование (first name / last name / zip), анализ переходов состояний (жизненный цикл бронирования и заказа) и предугадывание ошибок (неверный Content-Type, битый JSON, несуществующие ID). Примеры — в [test-design.md](test-design.md).

## 6. Окружение и инструменты

Ручное UI-тестирование я вёл в Chrome с DevTools. API тестировал в Postman и Newman, автотесты писал на Python 3.12 с pytest и requests. SQL-запросы проверял на SQLite 3.x (синтаксис совместим с PostgreSQL). Тест-кейсы и баг-репорты оформлены в формате для Test IT. CI запускает pytest через GitHub Actions.

## 7. Тестовые данные

В UI использую пользователей standard_user, locked_out_user и problem_user с паролем secret_sauce. В API — учётку admin / password123; бронирования создаю и удаляю в рамках теста. В БД — 15 клиентов, 22 счёта, 18 карт и 60 транзакций (см. sql/seed.sql).

## 8. Критерии входа и выхода

Вход: стенды доступны, тестовые данные подготовлены, тест-кейсы и чек-листы готовы. Выход считаю достигнутым, когда выполнены все smoke-проверки, пройдены позитивные тест-кейсы, для каждого дефекта есть воспроизведение и баг-репорт, нет открытых дефектов Blocker/Critical без обходного пути, а pytest-набор завершается без падений (известные дефекты помечены xfail).

## 9. Риски

Публичный API может быть нестабилен или недоступен — компенсирую повторным запуском, таймаутами и независимыми тестовыми данными. Данные стенда сбрасываются — поэтому создаю и удаляю данные внутри каждого теста. Демо-баги могут оказаться «задуманным поведением» — в отчёте я отмечаю, что стенд учебный, и воспроизвожу каждый дефект по шагам. При ограниченном времени приоритизирую так: smoke → позитив → негатив → исследовательское.
