# Проектная деятельность: формулировки для резюме

## Название проекта

**QA-проект: тестирование веб-приложения и REST API (SauceDemo, Restful-Booker)**  
Учебный проект: тест-дизайн, ручное тестирование UI, API-тестирование, оформление дефектов, SQL, стартовая автоматизация.

## Вариант для блока резюме (5–7 строк)

- Разработал 36 тест-кейсов и 76 чек-пунктов покрытия для UI и REST API, применяя классы эквивалентности, граничные значения, таблицу решений и попарное тестирование; оформил кейсы в формате, импортируемом в Test IT.
- Провёл ручное тестирование REST API в Postman: health-check, аутентификация, CRUD, фильтры, негативные сценарии; подготовил коллекцию из 15 запросов с 28 автопроверками.
- Выявил и оформил 14 дефектов (2 Critical, 10 Major) с воспроизведением, severity/priority и статусами по жизненному циклу дефектов; основные баги — отсутствие валидации типов и значений, приводящее к 500 и потере данных.
- Спроектировал учебную БД (4 таблицы, 60 транзакций) и написал 20 SQL-запросов: JOIN, LEFT JOIN, GROUP BY/HAVING, подзапросы, EXISTS/NOT EXISTS, оконные функции, DML с транзакциями; результаты проверены автоматическим скриптом.
- Автоматизировал регрессию API на pytest + requests: 27 тестов, из них 11 помечены xfail со ссылками на известные баги; настроил CI в GitHub Actions (документация, SQL, pytest, newman).

## Короткая версия (2–3 строки)

Учебный QA-проект по двум стендам: 36 тест-кейсов, 14 оформленных баг-репортов, Postman-коллекция и pytest-набор для REST API, 20 SQL-запросов к банкской схеме с автопроверкой результатов.

## Что я расскажу на собеседовании

Дефекты я искал исследовательским тестированием API: подавал неверные типы, пустые и некорректные значения. Пример — totalprice строкой возвращает 200 и сохраняет null, то есть сервер не валидирует тип и данные теряются (BUG-06). Отдельно я разбираю разницу между 500 и 400: пропуск обязательного поля возвращает 500 — это ошибка сервера, а не валидации, поэтому в ожидаемый результат баг-репорта я вынес 400 (BUG-01). Про приоритет и серьёзность приведу пример: потеря данных (null в цене) — Critical/High, а отсутствие ограничения длины имени — Minor/Low, хотя воспроизводятся оба одинаково надёжно. Каждый SQL-запрос из 20 проходит автопроверку ожидаемого числа строк и смысловых контрольных точек, весь прогон запускается командой python3 scripts/check_sql.py. Дальше я бы прогнал UI-кейсы вручную, добавил чек-лист по регрессии после каждого релиза и покрыл API смоуком в CI.
